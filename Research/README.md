# Research

This directory holds all research items in four states.

---

## Structure

```
Research/
├── _template.md        # Copy this to create a new item
├── backlog/            # Items not yet started
├── in-progress/        # Items actively being researched or under review
└── completed/          # Finished research with findings
```

---

## Submitting a Research Question (Primary Owner Path)

The owner submits new research questions through GitHub issues:

1. Create a new issue. Put the full research question in the issue body, along with any seeds or context that may help scope it.
2. Assign the issue to Copilot.
3. Copilot applies the `research-question` skill, creates a structured backlog item under `Research/backlog/`, and opens a PR. The agent scopes the question and stops; it does not conduct the research in this step.
4. Once the PR is merged, the `research-loop` workflow processes the backlog item. The workflow runs on weekdays and can also be triggered manually from the Actions tab.

### What Makes a Good Research Question?

A strong question passes all five checks:

| Check | A good question… |
|---|---|
| **Specific** | Names the subject, comparison or evaluation, and context. |
| **Answerable** | Can be resolved with evidence that is available in principle, rather than depending on future events or pure opinion. |
| **Scoped** | Sets explicit in-scope and out-of-scope boundaries. |
| **Motivated** | States the decision or problem the answer should inform. |
| **Decomposable** | Can be split into at least two atomic, evidence-based sub-questions. |

If a draft is too broad, the `research-question` skill suggests rewriting it in this form:

> What is the [best / most appropriate / correct] [X] for [purpose] given [constraints]?

The owner prefers questions to include seeds where available: starting points, links to related prior research items, concrete sources, or examples. These give Copilot material to use when scoping the question.

### Agent/Tooling Path: Add an Item Directly

The following file-copy workflow is for agents or other direct repository work. It remains available, but is not the primary way the owner submits a question:

```bash
cp Research/_template.md Research/backlog/$(date +%Y-%m-%d)-short-title.md
# Edit the file, fill in title, question, context
git add Research/backlog/ && git commit -m "research: add backlog item - <short title>"
```

## Workflow

### Starting an item

```bash
python -m src.main research start <filename>
# The command moves the file to in-progress/, updates status and started date,
# and stages the move in the git index automatically.
git commit -m "research: start - <short title>"
```

### Marking an item for review (draft)

When research is complete, mark the item for review. The file **stays in `in-progress/`**:

```bash
python -m src.main research draft <filename>
git add Research/in-progress/<filename>
git commit -m "research: draft - <filename>"
gh workflow run research-review.yml -f item_path=Research/in-progress/<filename>
```

### Completing an item (after review passes)

```bash
python -m src.main research complete <filename>
# Moves the file to Research/completed/, updates status and completed fields,
# and stages the move in the git index automatically.
git commit -m "research: complete - <short title>"
```

### Lifecycle

```
backlog → in-progress → reviewing → completed
               ↑_____________|
        (review fail: fix violations, run draft again)
```

`reviewing` items stay in `in-progress/`. The only directory move is the final `complete` step.

`YYYY-MM-DD-short-descriptive-title.md`

- `2026-02-27-youtube-transcript-fetching.md`
- `2026-03-01-information-synthesis-entropy.md`

## Output Types

Research can produce one or more outputs. Record in the `output:` field of the item:

| Output type | Description |
|---|---|
| `skill` | A new skill for `davidamitchell/Skills` |
| `tool` | A new or updated tool in `src/` |
| `agent` | A new agent configuration |
| `knowledge` | A structured note or ADR |
| `backlog-item` | Spawns one or more items in `BACKLOG.md` |

---

## Separating Research Backlog from Repo Improvement Backlog

- **`Research/backlog/`** — *what to research* (questions, topics, hypotheses)
- **`BACKLOG.md`** — *how to improve this repo* (code, tooling, structure)

Never mix these. A research item may *produce* a backlog item (e.g. "after researching SQLite, we decide to use it → add backlog item 3.2"), but the research item itself lives here.

## Consolidated Research Document

Completed research is automatically consolidated into a single master document:

**`Research/Research_Master.md`**

This file is generated by the [`consolidate_research` workflow](../.github/workflows/consolidate_research.yml) and contains:

- A table of contents (item titles, not filenames) in reverse chronological order
- Per-item sections with: title, tags, link to source file, research question, and high-signal sections (Methodology, Findings, etc.)

The workflow runs automatically on any push to `main` that touches `Research/completed/`, and can also be triggered manually from the Actions tab.

**Exclusions:** Items with `added` date before 2026-02-28 and filenames containing `meta` or `infra` are excluded.
