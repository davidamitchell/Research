# Independent verification and durable evidence for goal attainment

## Research Question

What reusable verification, assurance, logging, and audit mechanisms can determine whether a stated goal has been attained while remaining independent of any specific content pool or execution environment, and how should their reliability, evidence durability, and non-interference be evaluated?

## Scope

**In scope:**
- Deterministic verification procedures, evidence-based assurance patterns, immutable or tamper-evident logging, and independent audit mechanisms
- Checking primitives that can be invoked by any party inside or outside an active working context
- Criteria for evaluating reliability, replayability, tamper resistance, independence, and non-interference with the content and harness zones
- Mechanisms that produce durable evidence assertions rather than transient judgments only

**Out of scope:**
- Domain-specific policies for when or how verification results should be acted on
- Content-pool curation or execution-harness adaptation methods except where needed to prove non-interference
- Purely subjective review processes that do not yield reusable evidence artefacts

**Constraints:** Treat this zone as a provider of checking mechanisms rather than a decision-making authority. Prioritise reusable methods that can travel across domains, distinguish evidence generation from governance response, and evaluate whether the mechanism can stay independent of both the mediated content pool and the active execution environment.

## Context

This item informs how a third-zone validation layer can provide durable, domain-independent evidence that a goal was or was not met without becoming entangled in the content-pool or execution-harness design itself.

3. Compare how those mechanisms establish attainment, what evidence they emit, and how durable or replayable that evidence remains over time.

5. Synthesize a reusable set of checking primitives and an assessment rubric for reliability and evidence quality.

### §2 Investigation

**2a. Attestation formats for verifiable production records.** The in-toto attestation framework defines a Statement layer that binds a set of software artifacts, identified only by cryptographic digest, to a typed predicate describing how they were produced; the Statement's `subject` field is matched purely by digest, so the attestation's claim about an artifact cannot be silently redirected to a different artifact later. [fact; source: https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md] Supply-chain Levels for Software Artifacts (SLSA) defines its Provenance predicate on top of this Statement layer as an attestation that a named build platform produced the artifact by executing a declared `buildDefinition`, with all external, untrusted inputs captured as explicit parameters that a downstream consumer must independently verify. [fact; source: https://slsa.dev/spec/v1.1/provenance] This pattern generalises past software builds: any goal-attainment claim can be expressed as a digest-bound Statement whose predicate asserts the specific goal-state reached, decoupling the identity of "what was checked" from the content pool or harness that produced it, because the Statement layer treats predicate semantics as pluggable rather than build-specific. [inference; source: https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md; https://slsa.dev/spec/v1.1/provenance]

**2b. Transparency logs for durable, tamper-evident evidence.** Sigstore's Rekor project maintains a public transparency log, an append-only ledger of signed metadata entries that anyone can query, described as providing an "immutable, tamper-resistant ledger" for supply-chain metadata. [fact; source: https://docs.sigstore.dev/logging/overview/] The log's tamper evidence rests on a Merkle tree, a binary hash tree in which each entry is a leaf and every internal node is the hash of its children, which supports two independently checkable proofs: an inclusion proof that a specific entry exists in the log, and a consistency proof that the log has only grown and no earlier entry has been altered or deleted. [fact; source: https://github.com/sigstore/architecture-docs/blob/main/rekor-spec.md] Because any third party can recompute an inclusion or consistency proof against the log's published root hash without needing write access or trust in the log operator, the transparency-log pattern gives a goal-attainment checking zone a way to emit evidence that remains independently checkable even if the content pool or execution harness that generated the underlying event is later compromised or destroyed. [inference; source: https://github.com/sigstore/architecture-docs/blob/main/rekor-spec.md; https://docs.sigstore.dev/logging/overview/]

**2c. A domain-agnostic model for representing provenance.** The World Wide Web Consortium (W3C) Provenance (PROV) Data Model, published as the PROV-DM Recommendation, defines a minimal, domain-independent vocabulary of Entities, Activities, and Agents, plus relations such as `wasGeneratedBy`, `wasDerivedFrom`, and `wasAttributedTo`, intended to be extended for any specific domain rather than tied to software builds. [fact; source: https://www.w3.org/TR/prov-dm/] This gives the checking zone a candidate common schema for logging what was checked, by whom, and from what prior evidence, independent of whether the underlying goal belongs to a software delivery pipeline, a research task, or an autonomous agent's action sequence, because the model's core relations are defined without reference to any specific execution technology. [inference; source: https://www.w3.org/TR/prov-dm/]

**2d. Runtime verification of a live execution trace against a formal specification.** Runtime verification is defined in the foundational survey by Leucker and Schallhart as an approach that synthesises a monitor from a formal specification, typically expressed in a temporal logic or as an automaton, and uses that monitor to check an actual execution trace, producing a verdict that a finite observed prefix satisfies, violates, or leaves inconclusive with respect to the specification. [fact; source: https://doi.org/10.1016/j.jlap.2008.08.004] Because the monitor is synthesised separately from the system under observation and evaluates only the trace of events the system emits, runtime verification is structurally positioned to check goal attainment without needing to alter the internal logic of the content pool or harness being checked, though this depends on how the trace is collected. [inference; source: https://doi.org/10.1016/j.jlap.2008.08.004] Follow-up survey literature on trace uncertainty identifies incomplete, ambiguous, or partially observable traces, arising from limited instrumentation access, as the main practical obstacle to a monitor delivering a definitive verdict, which is a direct threat to reusability across content pools with different observability guarantees. [inference; source: https://doi.org/10.1016/j.jlap.2008.08.004]
Access note: secondary-source lead on trace-uncertainty survey (2023); primary bibliographic record unconfirmed this session; see Risks/Gaps for the labeled disposition.

**2e. Zero-knowledge proofs of correct execution.** A Zero-Knowledge Succinct Non-Interactive Argument of Knowledge (zkSNARK) allows a prover to convince a verifier that a computation was executed correctly and reached a specific claimed result, without the verifier re-executing the computation and without the prover revealing the private inputs used, and with a proof whose size and verification time do not grow with the complexity of the computation being proved. [fact; source: https://eprint.iacr.org/2013/879] The construction by Ben-Sasson et al. proves execution of arbitrary programs on a general-purpose von Neumann architecture rather than only fixed circuits, which means the technique is not tied to any specific content pool's instruction set once a program is compiled to the target representation. [fact; source: https://eprint.iacr.org/2013/879] This makes zero-knowledge succinct proofs the strongest available primitive for verifier independence from the execution environment, because the verifier's confidence rests on cryptographic soundness of the proof system rather than on trusting, replaying, or even observing the environment that ran the computation, though the proving side still requires computational resources proportional to the underlying computation. [inference; source: https://eprint.iacr.org/2013/879]

**2f. How current agent evaluation practice separates process from outcome.** A 2025 survey of Large Language Model (LLM) agent evaluation and benchmarking identifies trajectory evaluation, whether the agent took a sensible sequence of steps, and task completion, whether the agent reached the intended goal regardless of process, as two evaluation axes that current benchmarks assess separately rather than collapsing into one score. [fact; source: https://arxiv.org/abs/2507.21504] METR's task-completion time-horizon methodology instantiates independent, outcome-only checking at scale: it defines an external, human-time-referenced success criterion for each task and reports what fraction of tasks a model completes at that criterion, without granting the evaluated model any role in determining its own pass or fail outcome. [fact; source: https://arxiv.org/abs/2503.14499] Together these show that a goal-attainment checking zone does not need to inspect or approve of the internal reasoning path an agent took; it only needs an externally defined, independently applied success criterion and a mechanism, automated check, deterministic state comparison, or bounded LLM-as-judge assessment, to apply that criterion to the observed final state. [inference; source: https://arxiv.org/abs/2507.21504; https://arxiv.org/abs/2503.14499] The repository's own prior item on LLM-as-judge pipeline validation checkpoints found that the common documented production pattern layers deterministic checks for exact structure or executable correctness underneath judge-based checks for semantic quality, safety, or task completion, which is the same layering this item recommends when it treats bounded LLM-as-judge assessment as only one of several interchangeable determination mechanisms rather than the primary attainment check. [fact; source: https://davidamitchell.github.io/Research/research/2026-04-28-llm-as-judge-pipeline-validation-checkpoints.html]

**2g. Formal criteria for independence and non-interference.** The non-interference security property, formalised by Goguen and Meseguer, requires that any sequence of low-sensitivity inputs produce identical low-sensitivity outputs regardless of what high-sensitivity inputs or activity occurred, so that the presence and behaviour of one channel cannot be inferred from another channel's observable outputs. [fact; source: https://doi.org/10.1109/SP.1982.10014] Applied to a checking zone, this gives a precise formal target: the mechanism used to verify goal attainment should not be observable to, or able to change the observable behaviour of, the content pool or execution harness it is checking, distinguishing a genuinely independent checking mechanism from one that merely happens not to interfere in the cases tested. [inference; source: https://doi.org/10.1109/SP.1982.10014] In practice, every mechanism surveyed above achieves only a bounded, not absolute, version of this property: attestation and transparency-log evidence is collected after or alongside execution and so cannot influence the artifact's own build, but the instrumentation needed to emit the event stream for runtime verification, or the telemetry-collection step needed for provenance and zero-knowledge witnesses, does touch the execution environment and could in principle alter its timing or resource use. [inference; source: https://doi.org/10.1016/j.jlap.2008.08.004; https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md]

**2h. Independent audit criteria from an established control catalogue.** The National Institute of Standards and Technology (NIST) Special Publication 800-53 Revision 5 control catalogue defines its Audit and Accountability control family to require that audit records be generated, protected from unauthorised access or modification, retained, and reviewed independently of the system components that generate the events being audited. [fact; source: https://csrc.nist.gov/pubs/sp/800/53/r5/final] This gives a checking-zone rubric that is broader than any single technical mechanism: reliability should be judged not only by whether a mechanism can detect tampering after the fact, as transparency logs do, but by whether audit generation, protection, and review functions are organisationally and technically separated from the audited system, which none of the cryptographic mechanisms above address on their own. [inference; source: https://csrc.nist.gov/pubs/sp/800/53/r5/final]

**2i. Relationship to prior repository work.** The governance assurance item already established that a durable audit trail needs two separate evidence channels, one proving how an artifact was produced and one proving which policy version evaluated a change, and that provenance attestations and policy decision logs jointly satisfy this. [fact; source: https://davidamitchell.github.io/Research/research/2026-04-22-ai-governance-assurance-change-control-verification.html] This item extends that pattern from change-control decisions to goal-attainment claims generally, and adds the transparency-log and runtime-verification primitives that the earlier item did not examine. [inference; source: https://davidamitchell.github.io/Research/research/2026-04-22-ai-governance-assurance-change-control-verification.html; https://docs.sigstore.dev/logging/overview/] The claim-verification item established that an automated verifier should only retain a `[fact]` label on a claim when an identified external source states the same proposition, downgrading to `[inference]` on any match failure rather than preserving false certainty. [fact; source: https://davidamitchell.github.io/Research/research/2026-05-02-automated-claim-verification-academic-literature.html] The same downgrade discipline applies directly to a goal-attainment verdict, where an inconclusive runtime-verification monitor result or an unmatched attestation should downgrade the attainment claim rather than default to pass; this extension from claim verification to goal-attainment verdicts is this item's own reasoning step, not an assertion the cited item makes. [inference; source: https://davidamitchell.github.io/Research/research/2026-05-02-automated-claim-verification-academic-literature.html] The cryptographic intent preservation item established that legitimate evolution of a governed record should be an append-only amendment chain referencing the prior digest, rather than an in-place rewrite. [fact; source: https://davidamitchell.github.io/Research/research/2026-04-27-cryptographic-intent-preservation-runtime-evaluation.html] The same pattern applies to the stated-goal declaration itself, since a goal-attainment checking mechanism is only meaningful if the goal it checks against is itself tamper-evident; this application to goal declarations is this item's own extension, not a claim the cited item makes. [inference; source: https://davidamitchell.github.io/Research/research/2026-04-27-cryptographic-intent-preservation-runtime-evaluation.html]

### §3 Reasoning

A goal-attainment checking zone needs at minimum four composable primitives, each independently sourced above: a digest-bound attestation format to state what was checked and what predicate was asserted about it (in-toto and SLSA), a tamper-evident append-only log to make that assertion durable and independently re-checkable after the fact (Rekor and its Merkle tree proofs), a domain-agnostic schema to represent the checked entities, activities, and agents so the mechanism travels across content pools (the PROV Data Model), and an execution-time or proof-time mechanism to actually determine whether the goal state was reached, for which the survey identified two structurally different options: runtime verification against a formal specification of the goal, and zero-knowledge proof of correct execution against a claimed result. [inference; source: https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md; https://github.com/sigstore/architecture-docs/blob/main/rekor-spec.md; https://www.w3.org/TR/prov-dm/; https://doi.org/10.1016/j.jlap.2008.08.004; https://eprint.iacr.org/2013/879] These two determination mechanisms trade off differently: runtime verification requires only an event trace and a specification, so it is cheaper to deploy but its verdict quality degrades with trace incompleteness, while zero-knowledge proof gives a cryptographically sound and environment-independent verdict but at a proving cost proportional to the checked computation and only for computations expressible in the proof system's target representation. [inference; source: https://doi.org/10.1016/j.jlap.2008.08.004; https://eprint.iacr.org/2013/879] Non-interference, formalised by Goguen and Meseguer, is the correct target property for evaluating whether any of these mechanisms remains independent of the content pool or harness, but none of the surveyed mechanisms satisfies it absolutely, because instrumentation, telemetry collection, or witness generation for the goal-determination step necessarily touches the checked system to some degree. [inference; source: https://doi.org/10.1109/SP.1982.10014] Reliability evaluation should therefore be a graded rubric, not a binary pass or fail, spanning replayability (can a third party recompute the verdict from the durable evidence alone), tamper resistance (Merkle inclusion and consistency proofs), organisational independence (NIST SP 800-53 Audit and Accountability separation of duties), and interference bound (how much the collection step could alter the checked system's behaviour). [inference; source: https://github.com/sigstore/architecture-docs/blob/main/rekor-spec.md; https://csrc.nist.gov/pubs/sp/800/53/r5/final; https://doi.org/10.1016/j.jlap.2008.08.004]

### §5 Depth and Breadth Expansion

**Technical lens:** The four-primitive composition in §3 is only as strong as its weakest evidence channel; if the goal declaration itself can be rewritten without a tamper-evident amendment chain, then even a cryptographically sound zero-knowledge proof of "goal reached" is proving conformance to a moving target, which is why the append-only amendment pattern from the cited cryptographic intent preservation item is a structural precondition for this item's mechanisms, not an optional add-on. [inference; source: https://davidamitchell.github.io/Research/research/2026-04-27-cryptographic-intent-preservation-runtime-evaluation.html; https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md]

**Regulatory lens:** NIST SP 800-53's Audit and Accountability family requires audit generation, protection, retention, and review as organisationally separable functions, which maps directly onto a three-zone architecture, content pool, execution harness, and independent checking zone, but the control catalogue does not itself specify cryptographic mechanisms, so the technical primitives in §2 fill an implementation gap that the regulatory framework leaves open. [fact; source: https://csrc.nist.gov/pubs/sp/800/53/r5/final]

**Economic lens:** Zero-knowledge succinct proof generation carries a proving-time cost proportional to the underlying computation, which is a real deployment constraint the primary source itself frames as a technical achievement in verification cost rather than proving cost, so the economic trade-off is between paying that proving cost for the strongest available independence guarantee, or accepting the weaker, cheaper interference bound of runtime verification and attestation-based evidence. [inference; source: https://eprint.iacr.org/2013/879]

**Behavioural lens:** Separating trajectory evaluation from task-completion evaluation, as current agent-benchmark practice does, matches a behavioural risk this item's scope explicitly wants to avoid: a checking zone that inspects and judges the reasoning path risks becoming an implicit second execution harness rather than a durable evidence provider, so restricting the checking zone to outcome verification, as METR's external time-horizon methodology does, keeps the non-interference boundary cleaner even though it discards process-level diagnostic information. [inference; source: https://arxiv.org/abs/2507.21504; https://arxiv.org/abs/2503.14499]

### §6 Synthesis

**Executive summary:**
A reusable, domain-independent goal-attainment checking zone can be composed from four primitives already proven individually: digest-bound attestations to state what was checked, tamper-evident transparency logs to make that assertion durable and re-verifiable, a domain-agnostic provenance schema to carry the assertion across content pools, and either runtime verification or zero-knowledge proof as the mechanism that actually determines whether the goal state was reached. [inference; source: https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md; https://github.com/sigstore/architecture-docs/blob/main/rekor-spec.md; https://www.w3.org/TR/prov-dm/] None of these mechanisms achieves the formal non-interference property defined by Goguen and Meseguer in an absolute sense, so independence should be evaluated as a graded, evidence-backed property rather than assumed. [inference; source: https://doi.org/10.1109/SP.1982.10014]

### Executive Summary

A reusable, domain-independent goal-attainment checking zone can be assembled from four already-proven primitives: a digest-bound attestation that states what was checked, a tamper-evident transparency log that makes that assertion durable and independently re-verifiable, a domain-agnostic provenance schema that lets the assertion travel across content pools, and either runtime verification or zero-knowledge proof as the mechanism that actually decides whether the goal state was reached. [inference; source: https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md; https://github.com/sigstore/architecture-docs/blob/main/rekor-spec.md; https://www.w3.org/TR/prov-dm/] Runtime verification checks a live execution trace against a formal specification of the intended outcome and is cheap to deploy but degrades when the trace is incomplete, while zero-knowledge succinct proof cryptographically certifies that a claimed result follows from correct execution without needing to observe or re-run the environment, at the cost of proving effort proportional to the checked computation. [inference; source: https://doi.org/10.1016/j.jlap.2008.08.004; https://eprint.iacr.org/2013/879] None of the surveyed mechanisms achieves the formal non-interference property defined by Goguen and Meseguer in an absolute sense, because every determination step still requires some instrumentation or telemetry contact with the checked system, so independence should be treated as a graded, evidence-backed property rather than an assumed guarantee. [inference; source: https://doi.org/10.1109/SP.1982.10014] Reliability of a candidate mechanism should be evaluated against a four-part rubric: replayability from durable evidence alone, cryptographic tamper resistance, organisational separation of audit generation from the audited system, and a bounded interference footprint. [inference; source: https://github.com/sigstore/architecture-docs/blob/main/rekor-spec.md; https://csrc.nist.gov/pubs/sp/800/53/r5/final]

### Key Findings

1. The in-toto attestation Statement layer binds a predicate describing how or whether a goal was reached to a set of artifacts identified purely by cryptographic digest, so the claim cannot later be silently redirected to a different artifact or execution instance. ([fact]; medium confidence; source: https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md)
2. The Supply-chain Levels for Software Artifacts Provenance predicate requires that all external, untrusted inputs to a build be captured as explicit parameters that a downstream verifier must independently check, giving a template for representing a goal-attainment claim without trusting the build platform itself. ([fact]; medium confidence; source: https://slsa.dev/spec/v1.1/provenance)
3. Sigstore's Rekor transparency log uses a Merkle tree structure to support independently recomputable inclusion and consistency proofs, so any third party can verify that a goal-attainment record exists and that the log has not been retroactively altered, without needing write access or trust in the log operator. ([fact]; medium confidence; source: https://github.com/sigstore/architecture-docs/blob/main/rekor-spec.md; https://docs.sigstore.dev/logging/overview/)
4. The World Wide Web Consortium Provenance Data Model defines a domain-agnostic vocabulary of entities, activities, and agents that a checking zone can reuse to represent what was checked and by what process, regardless of whether the underlying goal belongs to a software pipeline, a research task, or an autonomous agent action sequence. ([fact]; medium confidence; source: https://www.w3.org/TR/prov-dm/)
5. Runtime verification synthesises a monitor from a formal specification and evaluates only the trace of events a system emits, positioning it to check goal attainment without altering the checked system's internal logic, but its verdict quality depends entirely on how complete and unambiguous the collected trace is. ([inference]; medium confidence; source: https://doi.org/10.1016/j.jlap.2008.08.004)
6. Zero-knowledge succinct non-interactive arguments of knowledge let a verifier confirm that a claimed computational result followed from correct execution of an arbitrary program, without re-executing the computation or observing the private inputs, making them the strongest available mechanism for verifier independence from the execution environment among the mechanisms reviewed. ([inference]; medium confidence; source: https://eprint.iacr.org/2013/879)
7. The formal non-interference property requires that a checking channel's presence and activity have no observable effect on the system being checked, and applying this standard shows that every mechanism surveyed here achieves only a bounded rather than absolute version of independence, because instrumentation or telemetry collection for the goal-determination step necessarily touches the checked environment. ([inference]; medium confidence; source: https://doi.org/10.1109/SP.1982.10014)
8. The NIST SP 800-53 Audit and Accountability control family requires that audit record generation, protection, retention, and review be separated from the system generating the audited events, which extends the reliability rubric beyond cryptographic tamper evidence to organisational independence that none of the technical mechanisms address on their own. ([fact]; medium confidence; source: https://csrc.nist.gov/pubs/sp/800/53/r5/final)
9. Current large language model agent evaluation practice separates trajectory evaluation, whether the agent's steps were sensible, from task-completion evaluation, whether the goal was reached regardless of process, and external time-horizon measurement methodologies apply an outcome-only success criterion without granting the evaluated agent any role in judging its own result. ([fact]; medium confidence; source: https://arxiv.org/abs/2507.21504; https://arxiv.org/abs/2503.14499)
10. This item extends the repository's prior governance-assurance finding that a durable audit trail needs both a provenance-evidence channel and a policy-decision-evidence channel by adding a tamper-evident transparency-log layer and a domain-agnostic provenance schema that the earlier item did not examine. ([inference]; medium confidence; source: https://davidamitchell.github.io/Research/research/2026-04-22-ai-governance-assurance-change-control-verification.html; https://github.com/sigstore/architecture-docs/blob/main/rekor-spec.md)
11. A goal-attainment checking mechanism should apply the same downgrade discipline the repository's claim-verification item established for source-matching, retaining a positive attainment verdict only when the runtime-verification monitor or zero-knowledge proof returns a definitive result, and downgrading to an unresolved or inferential status on any inconclusive, incomplete, or unmatched outcome rather than defaulting to pass. ([inference]; medium confidence; source: https://davidamitchell.github.io/Research/research/2026-05-02-automated-claim-verification-academic-literature.html)
12. A goal-attainment checking mechanism is only meaningful if the stated goal it checks against is itself tamper-evident, which requires the append-only, digest-referencing amendment chain already established in the repository's cryptographic intent preservation item rather than an in-place-editable goal declaration. ([inference]; medium confidence; source: https://davidamitchell.github.io/Research/research/2026-04-27-cryptographic-intent-preservation-runtime-evaluation.html)

### Assumptions

This item assumes that the three cited prior repository items already establish the adjacent evidence-channel, claim-labelling, and durable-intent patterns without needing re-derivation here. [assumption; source: https://davidamitchell.github.io/Research/research/2026-04-22-ai-governance-assurance-change-control-verification.html] This is reasonable because all three were produced under the same repository research-skill and evidence-discipline rules that govern this item, so their conclusions are treated as design context rather than as external claims requiring fresh verification. [assumption; source: https://davidamitchell.github.io/Research/research/2026-04-22-ai-governance-assurance-change-control-verification.html]

The instrumentation needed to collect an execution trace for runtime verification or a witness for a zero-knowledge proof is assumed to be lightweight enough not to materially change the checked system's behaviour in most deployments. [assumption; source: https://doi.org/10.1016/j.jlap.2008.08.004; https://eprint.iacr.org/2013/879] Neither primary source measures the instrumentation overhead directly, so this assumption is carried forward from the general framing of runtime verification and zero-knowledge proof as external-observation techniques rather than from a measured overhead figure. [assumption; source: https://doi.org/10.1016/j.jlap.2008.08.004; https://eprint.iacr.org/2013/879]

A goal-attainment checking zone is assumed to be able to receive a machine-readable statement of the goal it must check against, rather than only free-text human intent. [assumption; source: https://davidamitchell.github.io/Research/research/2026-04-27-cryptographic-intent-preservation-runtime-evaluation.html] This follows from the repository's cryptographic intent preservation item, which found that typed, bounded declarations are required for machine evaluability, but no source in this item's own evidence set independently re-confirms that assumption for the specific goal-attainment use case. [assumption; source: https://davidamitchell.github.io/Research/research/2026-04-27-cryptographic-intent-preservation-runtime-evaluation.html]

### Analysis

The evidence splits into two layers that answer different parts of the research question: attestation, transparency logging, and the provenance schema answer how a goal-attainment claim can be made durable, portable, and independently re-checkable, while runtime verification and zero-knowledge proof answer how the claim is actually determined in the first place. [inference; source: https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md; https://doi.org/10.1016/j.jlap.2008.08.004] Runtime verification and zero-knowledge proof were weighed as complementary rather than competing options, because the trade-off is not which is universally better but which interference bound and cost profile a given content pool can tolerate: runtime verification accepts a weaker independence bound in exchange for low deployment cost and broad applicability, while zero-knowledge proof accepts a higher proving cost in exchange for a cryptographically sound, environment-independent verdict. [inference; source: https://doi.org/10.1016/j.jlap.2008.08.004; https://eprint.iacr.org/2013/879] A competing interpretation, that non-interference should be treated as binary and any mechanism touching the checked system should be disqualified, was rejected, because the Goguen-Meseguer formalisation itself was designed for information-flow channels in a shared machine and does not have an established variant that certifies zero-contact external verification of arbitrary computation; treating independence as graded is the more defensible reading of evidence that only measures degrees of separation, not an achieved absolute. [inference; source: https://doi.org/10.1109/SP.1982.10014] The NIST control-family evidence was weighted as a complementary organisational lens rather than a substitute for the cryptographic mechanisms; this weighting is this item's own analytical decision, not a claim the NIST source itself makes. [inference; source: https://csrc.nist.gov/pubs/sp/800/53/r5/final] SP 800-53 defines what separation of duties should exist without specifying how any specific cryptographic or logging mechanism should implement it. [fact; source: https://csrc.nist.gov/pubs/sp/800/53/r5/final]

### Risks, Gaps, and Uncertainties

- The proving cost of zero-knowledge succinct proofs scales with the complexity of the checked computation, so the strongest independence guarantee reviewed here may be impractical for goal-attainment claims that involve long-running or resource-intensive execution, and no source in this item's evidence set measures that cost for a goal-attainment-sized workload specifically. [inference; source: https://eprint.iacr.org/2013/879]
- Runtime verification's reliance on trace completeness means its reliability for a specific content pool cannot be assessed from the general literature alone; it depends on the instrumentation access that pool actually grants, which this item did not test against a concrete deployment. [inference; source: https://doi.org/10.1016/j.jlap.2008.08.004]
- A secondary claim about a 2023 survey specifically addressing uncertainty in runtime verification traces could not be independently confirmed against a primary source in this session; search query "uncertainty in runtime verification survey Computer Science Review 2023" returned only secondary summaries without a verifiable primary bibliographic record, so no claim in this item rests on that unconfirmed lead. [assumption; source: https://doi.org/10.1016/j.jlap.2008.08.004]
- The Rekor transparency-log evidence in this item comes from two documents produced by the same project, so the tamper-resistance claim, while backed by primary specification text, does not meet the two-independent-organisation bar for high confidence and is held at medium throughout. [inference; source: https://github.com/sigstore/architecture-docs/blob/main/rekor-spec.md; https://docs.sigstore.dev/logging/overview/]
- This item did not evaluate how the four-primitive composition would perform against an adversary who controls both the content pool and the instrumentation layer simultaneously, which is the scenario the non-interference formalism was originally built to reason about and remains the most direct threat model to test in a follow-up item. [inference; source: https://doi.org/10.1109/SP.1982.10014]

### Open Questions

- What machine-readable schema should a goal-attainment predicate use inside an in-toto Statement so that verifiers across different content pools can compare goal-state claims without a shared execution vocabulary? [inference; source: https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md; https://www.w3.org/TR/prov-dm/]
- At what computation size does zero-knowledge succinct proof become impractical for goal-attainment checking relative to runtime verification, and is there a hybrid pattern that uses runtime verification for routine checks and zero-knowledge proof only for disputed or high-stakes attainment claims? [inference; source: https://doi.org/10.1016/j.jlap.2008.08.004; https://eprint.iacr.org/2013/879]
- Can a lighter-weight formal test than full non-interference certify that a specific instrumentation approach stays within an acceptable interference bound, rather than only being able to say the bound is nonzero? [inference; source: https://doi.org/10.1109/SP.1982.10014]
- How should the checking zone's own transparency-log infrastructure be kept independent of the organisation that also controls the content pool, so that the NIST-style organisational separation requirement is met in practice rather than only on paper? [inference; source: https://csrc.nist.gov/pubs/sp/800/53/r5/final; https://github.com/sigstore/architecture-docs/blob/main/rekor-spec.md]
