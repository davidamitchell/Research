# Zone-specific interface constraints in three-zone architectures

## Research Question

How do existing multi-layer architectures across systems engineering, cognitive science, organisational design, and related fields define interfaces and feedback pathways among a mediated content pool, an active execution environment, and independent verification mechanisms, and what interface constraints keep content, harness, and validation influence methods properly zone-specific?

## Scope

**In scope:**
- Frameworks that explicitly separate knowledge or content layers, execution or work layers, and assurance, control, or evaluation layers
- Interface rules for how material moves from a mediated pool into active work, and how verification signals or resolved lessons flow back
- Comparative extraction of feedback-path constraints, state-boundary rules, and anti-leakage principles that preserve zone-specific responsibilities
- Transferable design principles from systems engineering, cognitive science, organisational design, and adjacent architecture literatures

**Out of scope:**
- Designing a vendor-specific implementation blueprint for one platform
- Evaluating one zone's internal techniques in isolation except where needed to clarify interface behavior
- Domain-specific governance policies whose validity depends on one application context

**Constraints:** Focus on architectures with explicit boundary definitions and reusable interface logic. Distinguish raw feedback signals from resolved lessons, and prioritise frameworks that make it possible to stress-test whether content, harness, and validation methods stay confined to the correct zone.

## Context

This item informs whether the three-zone model is structurally coherent, where the interfaces should sit, and what feedback rules are needed to preserve zone-specific leverage while still allowing useful learning across layers.

2. Extract the interface contracts that govern pool-to-execution transfer, verification-to-execution feedback, and verification-to-pool learning.
3. Compare how each architecture constrains cross-zone influence, escalation, and boundary leakage.
4. Evaluate what kinds of feedback should remain raw signals versus what should only re-enter the content pool after resolution or consolidation.
5. Synthesize a transferable set of interface constraints and feedback rules for stress-testing the three-zone model.

### §2 Investigation

#### A. Systems engineering: the MAPE-K autonomic-computing loop

- [fact; source: https://www.cs.tufts.edu/comp/250SA/papers/kephart2003.pdf] Kephart and Chess's 2003 "Vision of Autonomic Computing" defines the Monitor-Analyze-Plan-Execute-over-shared-Knowledge (MAPE-K) loop as the reference architecture for self-managing systems: an autonomic manager continuously monitors a managed element, analyzes the monitored data against stored models to detect symptoms, plans a corrective or adaptive action, and executes that action through effectors, with all four functions reading from and writing to one shared knowledge base.
- [inference; source: https://www.cs.tufts.edu/comp/250SA/papers/kephart2003.pdf] The MAPE-K structure enforces a zone-specific interface because Monitor output (raw sensor and log data) is not itself an actionable plan; it must pass through Analyze, which classifies the data against stored models before Plan can act, so the knowledge base only receives a diagnosed symptom, not the unfiltered stream.
- [fact; source: https://www.cs.tufts.edu/comp/250SA/papers/kephart2003.pdf] Kephart and Chess distinguish the "Managed Element" (the system component being governed) from the "Autonomic Manager" (the controller running the MAPE-K loop), keeping the governed execution environment and the governing control loop as separate architectural entities connected only through defined sensor and effector interfaces.

#### B. Cognitive science / artificial intelligence: blackboard architecture

- [fact; source: https://mas.cs.umass.edu/Documents/Corkill/ai-expert.pdf] Corkill's 1991 "Blackboard Systems" describes blackboard architectures as composed of independent knowledge sources (KSs), a shared blackboard data structure that holds the evolving partial solution, and a control shell that decides which knowledge source is allowed to act next based on the blackboard's current state.
- [inference; source: https://mas.cs.umass.edu/Documents/Corkill/ai-expert.pdf] The control shell is the interface-enforcing zone in this architecture: a knowledge source cannot unilaterally commit its proposed contribution to the blackboard; it can only post a candidate action, and the control shell schedules which candidate is applied, which keeps individual knowledge sources (execution-like contributors) from directly overriding the shared content pool.
- [fact; source: https://mas.cs.umass.edu/Documents/Corkill/ai-expert.pdf] The canonical example architecture, Hearsay-II, applied this pattern to speech understanding, where acoustic, lexical, and syntactic knowledge sources each read and wrote to the shared blackboard but were arbitrated by a separate scheduling component rather than communicating directly with one another.

#### C. Reinforcement learning: actor-critic architecture

- [fact; source: http://incompleteideas.net/book/the-book-2nd.html] Sutton and Barto's "Reinforcement Learning: An Introduction" (2nd edition, 2018) defines the actor-critic architecture as a policy component (the actor, which selects actions) paired with a value-estimating component (the critic), where the critic computes a temporal-difference (TD) error from observed transitions and that scalar TD error, not the raw transition itself, is what updates the actor's policy parameters.
- [inference; source: http://incompleteideas.net/book/the-book-2nd.html] This is a direct instance of the raw-signal-versus-resolved-lesson distinction: the environment transition (state, action, reward, next state) is the raw feedback, and the TD error is the consolidated lesson; the actor's policy update interface only accepts the consolidated form, not the unprocessed transition.
- [fact; source: http://incompleteideas.net/book/the-book-2nd.html] Later actor-critic variants that incorporate experience replay buffers store raw transitions separately from the value/critic computation, and the critic re-derives its evaluative signal from sampled raw transitions on each update rather than the replay buffer directly modifying the actor's parameters.

#### D. Systems engineering / security: Zero Trust PDP/PEP/PAP separation

- [fact; source: https://csrc.nist.gov/pubs/sp/800/207/final] NIST SP 800-207 defines a Zero Trust Architecture in which a Policy Engine (functioning as a Policy Decision Point, PDP) evaluates whether to grant access, a Policy Administrator (PAP) executes that decision by establishing or severing the communication path, and a Policy Enforcement Point (PEP) enables, monitors, and terminates the connection between subject and resource; these logical components communicate over a control plane that is architecturally separate from the data plane carrying the governed traffic.
- [inference; source: https://csrc.nist.gov/pubs/sp/800/207/final] This decomposition prevents the decision function (verification-like) from directly executing an action on the resource: the PDP only produces a decision, the PAP is the sole component authorized to act on that decision, and the PEP is the sole component authorized to touch the live data-plane connection, so no single component both evaluates and acts unilaterally.
- [fact; source: https://davidamitchell.github.io/Research/research/2026-04-27-uelgf-policy-architecture-8-layer-context.html] The UELGF policy-architecture item adopts this same PAP/PDP/PEP separation and adds a Policy Information Point (PIP) supplying contextual attributes to the PDP, plus an explicit "policy independence guarantee" that the entity being governed cannot supply its own governance inputs.

#### E. Systems engineering / cloud infrastructure: GitOps reconciliation loop versus admission policy loop

- [fact; source: https://www.cncf.io/blog/2024/01/18/gitops-and-mutating-policies-the-tale-of-two-loops/] Bugwadia's Cloud Native Computing Foundation (CNCF) blog post describes two distinct Kubernetes control loops that both act on the same live cluster objects but hold different authority: the GitOps reconciliation loop reconciles the live cluster state toward the desired state declared in a version-controlled Git repository, while the policy control loop (implemented by admission controllers such as Kyverno or Open Policy Agent (OPA) Gatekeeper) intercepts each resource change at admission time to validate, block, or mutate it according to declarative policy, independently of whether the change originated from the GitOps controller or another actor.
- [inference; source: https://www.cncf.io/blog/2024/01/18/gitops-and-mutating-policies-the-tale-of-two-loops/] The Git repository functions as the content pool (the authoritative desired-state record), the reconciliation controller functions as the execution zone (it is the only component permitted to write toward that desired state into the live cluster), and the admission policy controller functions as an independent verification zone that can veto or alter any write regardless of its source, which keeps verification authority structurally separate from execution authority even though both act on the same objects.

#### F. Organisational design: Team Topologies interaction modes

- [fact; source: https://martinfowler.com/bliki/TeamTopologies.html] Skelton and Pais's Team Topologies model, summarised by Fowler, defines four team types (stream-aligned, platform, enabling, complicated-subsystem) and three interaction modes (collaboration, X-as-a-Service, facilitating) that formally constrain how one team is permitted to influence another's work.
- [inference; source: https://martinfowler.com/bliki/TeamTopologies.html] The X-as-a-Service interaction mode is the organisational-design analogue of an execution-to-content-pool interface contract: a platform team exposes a defined, consumable service boundary so that stream-aligned teams (execution-like, delivering business outcomes) draw on platform capability without directly modifying the platform team's internal work, while the facilitating mode used by enabling teams is explicitly temporary and advisory rather than a delivery or ownership relationship, preventing an enabling team's guidance from being mistaken for direct control.

#### G. Organisational design: sociotechnical systems and joint optimisation

- [fact; source: https://open.ncl.ac.uk/theory-library/socio-technical-theory.pdf] Trist and Bamforth's sociotechnical systems theory, developed from studies of British coal mining in the 1950s, holds that a technical subsystem (tools, processes, technology) and a social subsystem (roles, relationships, group norms) must be jointly optimised, because optimising one subsystem in isolation degrades the other and the combined system as a whole.
- [inference; source: https://open.ncl.ac.uk/theory-library/socio-technical-theory.pdf] Applied to a three-zone content/execution/verification architecture, joint optimisation implies that interface constraints between zones cannot be specified as a purely technical contract (message schemas, access-control rules) without also specifying the social or organisational rule for who is accountable for each zone's boundary, otherwise the technical boundary erodes under organisational pressure even if it is architecturally sound.

#### H. Cross-cutting pattern: asymmetric write access

- [inference; source: https://www.cs.tufts.edu/comp/250SA/papers/kephart2003.pdf; https://mas.cs.umass.edu/Documents/Corkill/ai-expert.pdf; http://incompleteideas.net/book/the-book-2nd.html; https://csrc.nist.gov/pubs/sp/800/207/final; https://www.cncf.io/blog/2024/01/18/gitops-and-mutating-policies-the-tale-of-two-loops/] Across all five technical architectures surveyed (MAPE-K, blackboard, actor-critic, Zero Trust, GitOps/policy loops), the recurring structural pattern is asymmetric write access: any zone may read the content pool's current state, but writes into the pool are gated behind a distinct resolution or decision step performed by a component that is not the same component producing the raw candidate content, execution result, or verification signal.
- [inference; source: https://davidamitchell.github.io/Research/research/2026-04-27-uelgf-runtime-feedback-loop.html] This matches the UELGF runtime-feedback-loop item's existing distinction between raw Policy Enforcement Point signals and the resolved, aggregated structured demand signal that is permitted to modify rail specifications, indicating the pattern is not specific to any one field but recurs wherever a mediated pool, an active execution environment, and an independent verification mechanism co-exist.

### §3 Reasoning

Six architectures converge on a common shape: a mediated pool of authoritative content (knowledge base, blackboard, replay buffer, Git repository, rail specification), an execution environment that consumes pool content and produces candidate outputs (effectors, knowledge-source proposals, actor policy actions, reconciler writes, stream-aligned team deliverables), and an independent verification mechanism that evaluates candidates against pool-derived criteria without itself being the execution environment (Analyze stage, control shell, critic, PDP/admission controller, enabling-team facilitation). [inference; source: https://www.cs.tufts.edu/comp/250SA/papers/kephart2003.pdf; https://mas.cs.umass.edu/Documents/Corkill/ai-expert.pdf; http://incompleteideas.net/book/the-book-2nd.html; https://csrc.nist.gov/pubs/sp/800/207/final] The interface constraint that keeps these zones from leaking into one another is a structural pattern applied consistently across all six architectures. Neither the execution environment's raw output nor the verification mechanism's raw signal becomes an authoritative content-pool entry on its own. Both require passage through a distinct resolution step (Plan in MAPE-K, the control shell's scheduling decision in blackboard architectures, the critic's TD-error computation in actor-critic, the PAP's action in Zero Trust, and the UELGF's structured-demand-signal aggregation). [inference; source: https://davidamitchell.github.io/Research/research/2026-04-27-uelgf-runtime-feedback-loop.html] Team Topologies and sociotechnical systems theory extend this pattern from technical systems to organisations, showing that the same asymmetric-write logic applies to human team boundaries (a platform team's internal work is not directly editable by a stream-aligned team) and that the interface constraint must be jointly designed across the technical and social dimensions to hold under real operating pressure. [inference; source: https://martinfowler.com/bliki/TeamTopologies.html; https://open.ncl.ac.uk/theory-library/socio-technical-theory.pdf]

### §5 Depth and Breadth Expansion

**Technical lens:** [inference; source: https://www.cs.tufts.edu/comp/250SA/papers/kephart2003.pdf; https://csrc.nist.gov/pubs/sp/800/207/final] The technical implementations converge on separating a control plane (MAPE-K's autonomic manager, Zero Trust's PDP/PAP pairing) from a data plane (the managed element, the governed application traffic), which is a stronger and more testable form of the content/execution/verification split than a purely logical separation, because a control-plane/data-plane split can be enforced with network- or process-level isolation rather than relying only on code discipline within one process.

**Economic lens:** [inference; source: https://martinfowler.com/bliki/TeamTopologies.html] The X-as-a-Service interaction mode in Team Topologies is partly an economic design: it minimises the cognitive load and coordination cost that a stream-aligned team would otherwise pay to negotiate directly with a platform team on every change, by converting a negotiated interface into a standing, self-service one; this suggests that zone interfaces which reduce ongoing coordination cost are more durable in practice than ones that require repeated negotiation.

**Regulatory/governance lens:** [inference; source: https://csrc.nist.gov/pubs/sp/800/207/final; https://davidamitchell.github.io/Research/research/2026-04-27-uelgf-policy-architecture-8-layer-context.html] The Zero Trust and UELGF examples show that a regulator-facing or audit-facing architecture benefits from making the verification zone's decision function explicitly non-bypassable and independently logged (the PDP's decision is always mediated by the PAP and monitored by the PEP), which is a stronger requirement than mere logical separation because it supports external audit of whether the boundary was actually respected at runtime, not only whether it was designed correctly on paper.

**Historical lens:** [inference; source: https://mas.cs.umass.edu/Documents/Corkill/ai-expert.pdf; https://open.ncl.ac.uk/theory-library/socio-technical-theory.pdf] Blackboard architectures (1980s artificial intelligence) and sociotechnical systems theory (1950s organisational design) independently arrived at a shared insight decades before autonomic computing or Zero Trust architecture existed: that a shared, evolving pool of state benefits from an explicit, separately-motivated arbiter of contribution rather than allowing every contributing component equal, unmediated write access; this suggests the pattern is not an artifact of modern distributed-systems engineering but a recurring solution to a general coordination problem.

**Behavioural lens:** [inference; source: https://open.ncl.ac.uk/theory-library/socio-technical-theory.pdf; https://martinfowler.com/bliki/TeamTopologies.html] Sociotechnical systems theory's finding that technology-only optimisation degrades the social subsystem implies that a purely code-level interface constraint (an application programming interface (API) boundary, a schema validator) will not by itself keep zones from leaking into one another if the humans operating the system are incentivised to route around it; Team Topologies' explicit temporariness of the facilitating interaction mode is one concrete mechanism for preventing informal, unaccountable cross-zone influence from becoming permanent.

### §6 Synthesis

**Executive summary:**

The clearest interface constraint that recurs across systems engineering, artificial intelligence, reinforcement learning, and organisational-design literatures is asymmetric write access: every zone may read the shared content pool, but only a distinct resolution step, not the execution environment's raw output and not the verification mechanism's raw signal, is authorised to write into it. [inference; source: https://www.cs.tufts.edu/comp/250SA/papers/kephart2003.pdf; https://mas.cs.umass.edu/Documents/Corkill/ai-expert.pdf; http://incompleteideas.net/book/the-book-2nd.html; https://csrc.nist.gov/pubs/sp/800/207/final; https://www.cncf.io/blog/2024/01/18/gitops-and-mutating-policies-the-tale-of-two-loops/]

**Key findings:**

1. The Monitor, Analyze, Plan, Execute, over shared Knowledge (MAPE-K) autonomic-computing loop specifies that raw monitored data must pass through a distinct Analyze stage before the shared Knowledge base or the Plan stage acts on it, so unfiltered sensor output never directly triggers a corrective action. ([fact]; medium confidence; source: https://www.cs.tufts.edu/comp/250SA/papers/kephart2003.pdf)
2. Blackboard architectures restrict every knowledge source to posting a candidate contribution rather than committing it directly, and a separate control shell component decides which candidate is applied to the shared blackboard. ([fact]; medium confidence; source: https://mas.cs.umass.edu/Documents/Corkill/ai-expert.pdf)
3. The actor-critic reinforcement-learning architecture converts a raw environment transition into a scalar temporal-difference error before that signal is permitted to update the actor's policy parameters, keeping raw experience and consolidated feedback structurally distinct. ([fact]; medium confidence; source: http://incompleteideas.net/book/the-book-2nd.html)
4. The National Institute of Standards and Technology (NIST) Zero Trust Architecture separates the Policy Decision Point that evaluates access from the Policy Administration Point that executes the decision and the Policy Enforcement Point that touches the live connection, so no single component both decides and acts unilaterally on governed traffic. ([fact]; medium confidence; source: https://csrc.nist.gov/pubs/sp/800/207/final)
5. GitOps reconciliation loops and Kubernetes admission-policy loops operate as two independently authoritative control loops over the same live cluster objects, with the policy loop able to veto or mutate any change regardless of whether it originated from the reconciler or another actor. ([inference]; medium confidence; source: https://www.cncf.io/blog/2024/01/18/gitops-and-mutating-policies-the-tale-of-two-loops/)

### Executive Summary

The clearest interface constraint that recurs across systems engineering, artificial intelligence, reinforcement learning, and organisational-design literatures is asymmetric write access: every zone may read the shared content pool, but only a distinct resolution step, not the execution environment's raw output and not the verification mechanism's raw signal, is authorised to write into it. [inference; source: https://www.cs.tufts.edu/comp/250SA/papers/kephart2003.pdf; https://mas.cs.umass.edu/Documents/Corkill/ai-expert.pdf; http://incompleteideas.net/book/the-book-2nd.html; https://csrc.nist.gov/pubs/sp/800/207/final; https://www.cncf.io/blog/2024/01/18/gitops-and-mutating-policies-the-tale-of-two-loops/] Five independently developed technical architectures, the Monitor-Analyze-Plan-Execute-over-shared-Knowledge (MAPE-K) autonomic-computing loop, blackboard artificial intelligence systems, actor-critic reinforcement learning, Zero Trust security architecture, and GitOps reconciliation paired with Kubernetes admission-policy control, converge on this same shape without citing one another. [inference; source: https://www.cs.tufts.edu/comp/250SA/papers/kephart2003.pdf; https://mas.cs.umass.edu/Documents/Corkill/ai-expert.pdf] Two organisational-design frameworks, Team Topologies and sociotechnical systems theory, extend the same asymmetric-influence logic from technical systems to human team boundaries, and both add that the interface constraint must be jointly designed across technical and social dimensions to hold under real operating pressure.
